# 榜单按小时存储与批量写入

服务端每 2 秒处理一批上传。先按账号和来源设备查出已保存的数据时间，再比对当批涉及的小时，把同一个小时的多次更新合成一次写入。四张榜共用一个整点截止时间。

## 数据库

测试服和正式服各有一个 SQLite 库。榜单使用两张固定的表，小时由时间列表示。

| 表 | 保存内容 |
| --- | --- |
| `leaderboard_data` 榜单数据 | 每个账号、每个来源、每个小时存一行。保存这个小时的 Token 小计、数据更新时间、最近接受的上传时间和编号，以及该小时最快的有效测速和对应信息。 |
| `leaderboard_results` 榜单结果 | 以截止时间 `cutoff_at` 为键，保存实际生成时间 `generated_at` 和四张榜的 `payload`。正常保留最新和上一份成功结果。 |

数据表用 `account_id + source_guid + hour_start` 唯一定位一行。账号 ID 由登录凭证确定，查询时向 `accounts` 取用户名。管理和登录信息由已有的账号、会话和管理表提供。

| 榜单数据列 | 用法 |
| --- | --- |
| `account_id`、`source_guid`、`hour_start` | GitHub 数字 ID、数据来源 GUID、小时起点。时间统一存 Unix 毫秒。 |
| `tokens`、`usage_updated_at`、`covered_until` | 此小时的 Token 小计、这份小计的更新时间、已经完整读取到的时刻。 |
| `last_upload_at`、`last_upload_id` | 此行最后成功写入的服务器时间和上传编号。最近上传时间取账号下的最新值。 |
| `best_speed`、`speed_at`、`speed_tokens`、`speed_model`、`speed_harness`、`speed_id` | 此小时最快的有效测速和那次测速的原始信息。24 小时用量榜的近期速度曲线使用同一小时行内短期保留的测速点。 |
| 来源进度 | `hour_start = 0` 专门保留给每个来源的进度行，保存此来源已确认的数据时间、当前上报电脑、上报资格编号和到期时间。小时统计和清理从正时间戳的行中取数。 |

`hour_start` 建索引，让用量榜可以按范围查小时数据。批次读取和更新使用唯一键。保留最近 720 个完整小时及当前小时的用量，清理超过 24 小时的速度记录。短期采样保留到已生成使用它的整点结果。

## 插件上传

插件通过登录凭证关联账号，一包对应一个来源 GUID。本机用自己的设备 GUID，SSH 用远端用户目录里已有的 GUID。SSH 包还带上报电脑的 GUID 和本次上报资格编号。

每包带上传编号和变化的小时。每个小时提供归属小时、读到的覆盖终点、这份汇总的更新时间、完整小计以及扫描是否成功。同一小时的 Token 值是本次完整扫描范围内的总数，含新输入、输出和缓存读写。跨小时的请求按完成时间归入对应小时。每个上报者按来源顺序扫描和保存结果。插件保存待传包，超时重试时沿用原编号、时间和内容。

归属小时决定写哪一行。`usage_updated_at` 取来源完成本次扫描时的时间，SSH 同一来源用远端时钟。服务器接收时刻另存为 `last_upload_at`。时钟回拨时，服务器返回该小时已保存的更新时间。插件重新完整扫描后，在该时间基础上生成严格递增的新更新时间。

保留现有上传入口，通过单独的能力标志协商小时格式。小时格式使用独立的格式号，服务端可以同时接收迁移中的旧包。

## 每两秒处理一批

| 步骤 | 处理规则 |
| --- | --- |
| 收包 | 解析批次里的包，按登录账号、来源和小时收集本次涉及的键。 |
| 一次读这一批的进度 | 写入线程开始事务，按账号和来源批量读取进度，再批量取出这批涉及的小时行。进度只用于定位和判断上报资格。决定能否更新时，用对应小时那一行的时间来比。 |
| 按小时比对 | 对还没有记录的有效小时插入小计。已有记录时，完整扫描的更新时间更晚、覆盖终点至少与旧值一样新，就替换原小计。数据一样的重发直接确认，较旧的结果保留原值。同一更新时间出现不同内容时保留已确认值，请插件重新扫描。 |
| 合并并写入 | 同一来源、同一小时只写一行。用量取通过校验后最新的完整小计，速度取所有有效候选里最快的一笔。复用准备好的写入语句，把小时行和来源进度一起提交。SQLite 提交成功后再回复插件。 |

比如设备已上传到今天 11 点，昨天 10 点的小时行仍然可以补传。昨天这一行缺失时插入。已有这一行时，与昨天这一行的时间和覆盖比对。同一批里一个小时的较早完整小计是 700，较新完整小计是 900，提交后的值是 900。

当前小时允许上传截至已完整读取时刻的小计。服务端能用覆盖终点识别已经读到哪里。日志读到一半或读取失败时保留上次确认的结果。完整扫描确认某小时没有用量后，可以用更新的零值更正旧值。

## A、B 共用 SSH

同一个 GitHub 账号下，A、B 连同一个 SSH 用户，使用同一个远端 GUID。服务器记录该来源当前有资格上报的电脑。资格有效期沿用 60 秒，成功采集可续期。接手时分配新的资格编号，覆盖前先从远端重新完整扫描对应小时。旧电脑迟到的包由资格编号识别。

A 扫到 100 条而 B 扫到 200 条时，以当前上报电脑对同一小时完整读取的结果为准。接手方没读齐时，沿用服务器已经确认的值。如果完整重读后结果变小，也可以用更新且覆盖充分的小计纠正旧值。两台电脑的本机数据各用各自的 GUID。

## 整点发布

每到整点，写入线程先提交收到时间早于整点的待写包。读线程固定这次 SQLite 读取的内容后，写入线程继续处理整点及之后的包，读线程在自己的读取中生成四张榜。用量分别加总截止前 24、168、720 个完整小时，截止时间本身归入下一小时。正常发布时，截止后到达的补传在下一次生效。

速度样本保存自己的测速编号和首次生成时刻，跨整点重发沿用这两项。速度是否合格沿用现有门槛，新增用量超过 500 Token 且平均速度为有效正数。每个小时保存最快的有效样本和它的模型、Harness、新增 Token、测速时间。速度榜在已结束的 24 小时里取每个账号最快一条，再排前 20。同速依次用测速时间、账号 ID 和样本编号定顺序。

四张榜及截止时间作为一份结果发布。写完新结果后保留上一份。计算失败或重启时继续提供最近的有效结果，用补算时已确认的数据生成最近整点的结果，并记录实际生成时间。封禁、清分等管理操作立即使受影响的结果失效，并按同一截止时间重算。

## 切换与验收

先用测试服数据库副本验证旧数据转换、批量写入和结果发布。能按时间和来源归属的用量按小时汇总。旧包中合在一起的本机与 SSH 用量由新版插件从日志按来源补传，已有每日总量用于核对。日志暂时读不齐的账号继续从旧表取用量，等补齐或旧数据移出 30 天范围后再切换。切换以账号为单位在一次事务中启用新数据。迁移期间，新旧结构用同一个整点窗口取数，再统一排名。旧速度样本按原账号参与排名，满 24 小时后退榜。保留切换前的数据库备份和服务版本供回退，正式服上线另外安排。

| 场景 | 通过条件 |
| --- | --- |
| 批里有同一来源同一小时的两个包 | 只更新一个小时行，保留时间较新的完整小计和最好的有效测速。 |
| 旧小时迟到与重复发送 | 缺失的旧小时可以补入。旧版本和重复包不改变已经确认的用量，写入失败也不会提前确认。 |
| 共用 SSH、断线、接手 | A、B 读到不同数量时，已有完整小计能保留到接手方读全。旧上报电脑迟到的包不会覆盖接手后的值。 |
| 整点与重启 | 四张榜使用同一截止时间，24、168、720 小时边界正确。重启和发布失败后仍能读取最近有效结果。 |
| 数据对齐 | 对测试服副本以同一截止时间核对三个用量榜和每人一条的速度榜。迁移中断后继续使用有效的旧数据。 |
